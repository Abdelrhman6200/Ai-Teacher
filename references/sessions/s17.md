## Goal and outcomes

**Goal.** The learner designs a context budget for a long-running workload and cuts its cost and drift with caching, compaction and just-in-time retrieval.

**You will be able to:**
- Design a context budget: what is always loaded, what is fetched on demand and what is dropped
- Place cache breakpoints so the stable prefix is reused, and verify hits from the usage fields
- Choose between context editing, compaction, memory and sub-agents for a task that overflows

## Key points

- Context engineering. Aim for the smallest set of high-signal tokens that makes the right behaviour likely. More context is not better: accuracy can fall as the window fills with noise (context rot).
- Load a little, fetch the rest. Keep the system prompt, tools and standing rules short and stable. Pull files, records and search results in just in time with search, glob or grep tools instead of pasting everything.
- Prompt caching. A cache read costs a fraction of normal input: 0.025 times base for Fable 5.2, 0.05 times for Opus 5.5 and Sonnet 5.5, 0.1 times for Haiku 5.5. A 5-minute cache write costs 1.25 times base and a 1-hour write 2 times. The default lifetime is 5 minutes and is refreshed on every hit.
- The cache matches the prefix in order: tools, then system prompt, then messages. Changing any block at or before a breakpoint invalidates everything after it, so put stable content first and volatile content (timestamps, user text) last.
- Overflow. Context editing clears old tool results. Compaction summarises older turns on the server. The memory tool keeps facts in files outside the window. A sub-agent works in its own context and returns a summary.
- Cache diagnostics are generally available (23 September 2026). Add the diagnostics object to a request and the response reports where the prompt prefix diverged from the previous request, so you can find the block that broke the cache. Include it on every turn.

## Context budget

| Layer | What goes in | Rule |
|---|---|---|
| Always loaded | System prompt, tool definitions, standing rules | Short and stable: this is the cacheable prefix |
| Fetched on demand | Files, records, search results | Load with search, glob or grep tools just in time |
| Carried in history | Turns and tool results | Clear or compact once they have served their purpose |
| Kept outside | Notes, progress files, memory | Write to a file and read it back when needed |

Aim for the smallest set of high-signal tokens that makes the right behaviour likely.

## Cache prices

| Event | Cost relative to base input |
|---|---|
| 5-minute cache write | 1.25 times |
| 1-hour cache write | 2 times |
| Cache read | 0.025 times Fable 5.2, 0.05 times Opus 5.5 and Sonnet 5.5, 0.1 times Haiku 5.5 |
| Uncached input | 1 times |

Check the pricing page for your model: the read multiplier differs by model. Caching and Batch discounts stack.

A cache pays off when the same prefix is read more than once inside its lifetime.

## Place the breakpoint

1. Put stable content first: tools, then the system prompt, then fixed documents.
2. Put volatile content last: timestamps, user text, per-request values.
3. Mark the last block that is identical across requests with cache_control, or use automatic caching.
4. Keep the cached blocks byte-identical between calls.
5. Send the next call inside the lifetime: 5 minutes by default, or choose 1 hour.
6. Confirm with cache_creation_input_tokens and cache_read_input_tokens.

Any change at or before a breakpoint invalidates everything after it.

## Which fix for which overflow

| Problem | Use |
|---|---|
| Old tool results pile up | Context editing: clear tool results |
| The whole conversation nears the window | Compaction: a server-side summary |
| Facts must outlive the session | Memory tool: files outside the window |
| A side task floods the context | Sub-agent: own context, returns a summary |
| Too many tool definitions | Tool search: load definitions on demand |

Clearing tool results or thinking blocks changes the prefix and can invalidate the cache. Clear enough at once to be worth the rewrite.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| A timestamp at the top of the system prompt | The first block changes, so nothing after it is cached | Move it to the end |
| Pasting whole files "just in case" | Noise crowds out the signal | Fetch the file when needed |
| Editing earlier turns | A change before a breakpoint breaks the cache | Only append |
| Never checking hit rates | The saving is assumed, not measured | Read cache_read_input_tokens |

## Cheat sheet

**Know**
- Smallest set of high-signal tokens. Fetch just in time.
- The cache is an ordered prefix: tools, system, messages. An early change breaks it.
- 5-minute write 1.25 times, 1-hour write 2 times, read 0.025 to 0.1 times by model.
- Overflow: clear tool results, compact, keep memory files or use sub-agents.

**Do**
- Write the context budget on one page.
- Add a breakpoint and read both usage fields.
- Break the cache on purpose and note the effect.
- Choose an overflow strategy and justify it.

## Going further

- Compaction works with caching: put a breakpoint at the end of the system prompt so only the summary is written again when compaction fires.
- Clearing tool results or thinking blocks invalidates the cache from the point of clearing. Use a minimum-clear setting so each clear is worth the rewrite.
- Changing the effort level between requests can invalidate the cache. Per-message effort (beta) keeps it.
- Minimum cacheable length differs by model: 512 tokens on Fable 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5. A shorter prompt is processed without caching and returns no error, so check that cache_creation_input_tokens or cache_read_input_tokens is above zero.
