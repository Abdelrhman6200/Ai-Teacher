# Session 23: Cost, latency and reliability engineering

Level 5: Expert (beyond 100). Deliverable: A cost model, a before-and-after optimisation table, a reliability test and a model upgrade decision. Worth: pass or fail, no points.

Contents: Goal and outcomes, Key points, Plain-language glossary, Free wins and trade-offs, Batch API facts, Build a cost model, Reliability checklist, Upgrade a model, Worked demo: cut one cost line safely, Common mistakes, Cheat sheet, Exercises, Case to attempt, Vocabulary, Score ladder (what your work looks like at each level), Going further, Study sources, Self-check questions, Exit ticket.

## Goal and outcomes

**Goal.** The learner cuts cost and latency without losing quality, keeps the system working through failures and limits, and upgrades models by test.

**You will be able to:**
- Build a cost model per run and per month, and cut it with free wins before trade-offs
- Keep a system reliable under rate limits, errors and timeouts
- Migrate to a new model by running the eval, not by trusting the name

## Key points

- Measure, then cut. Cost per run is input, cache and output tokens times price, plus tool calls and retries. Read it from the usage fields for each feature. Take the free wins first: caching, tidy prompts and outputs, Batch for non-urgent work. Then the trade-offs: a smaller model, lower effort, output caps and session budgets.
- Batch API. It takes 50 percent off input and output for asynchronous work, up to 100,000 requests or 256 MB per batch. Most finish within an hour and unfinished batches expire after 24 hours. The discount stacks with caching, but cache hits in a batch are best effort. Managed Agents get no batch discount.
- Latency. Choose a faster model for the step, trim input and output tokens, stream the response, lower effort and cache the prefix. Send easy steps to a small model and hard ones to a larger one, and run independent calls in parallel.
- Reliability. Retry rate-limit and overload errors with backoff and a cap, set timeouts, make operations idempotent, keep a fallback model and use spend limits as a backstop. Know your limits: requests, input tokens and output tokens per minute by tier. Workspaces (up to 100) separate teams and environments, and the default workspace cannot have spend limits.
- Upgrades are migrations. Read the model's migration guide, set effort explicitly, remove thinking settings the new model rejects, replace forced tool choice, rerun the evals and compare cost and latency, then switch behind a flag with a rollback. Check each model's lifecycle every month.
- Fast mode (speed: "fast") gives up to 2.5 times output speed at a higher price: Fable 5.2 costs $16 and $80 per million tokens in fast mode against $8 and $40 standard. It is a latency lever, not a cost lever. When you move between model families, rebuild the cost model from the usage fields, because the same text can cost more tokens.

## Plain-language glossary

| Term | Meaning | Think of it as |
|---|---|---|
| Free win | A saving with no quality loss | A coupon |
| Trade-off | A saving that costs some quality or speed | A cheaper cut of meat |
| Backoff | Waiting longer between each retry | Knock, then wait longer |
| Workspace | A partition with its own keys and limits | A department budget |

## Free wins and trade-offs

| Kind | Lever | Effect |
|---|---|---|
| Free win | Prompt caching | Cheaper repeated prefix |
| Free win | Tidy prompts and outputs | Fewer tokens |
| Free win | Batch for non-urgent work | Half price |
| Trade-off | A smaller model | Cheaper, needs an eval |
| Trade-off | Lower effort | Faster, may lose quality |
| Trade-off | Output caps and session budgets | Bounds the worst case |

Take the free wins first. Test every trade-off.

## Batch API facts

| Fact | Value |
|---|---|
| Discount | 50 percent on input and output |
| Size | Up to 100,000 requests or 256 MB |
| Speed | Most batches finish within an hour |
| Expiry | Unfinished batches expire after 24 hours |
| Caching | Stacks, but hits are best effort |

Never for anything a user is waiting on.

## Build a cost model

1. List every call in one run.
2. Record input, cache read, cache write and output tokens.
3. Multiply by the price for the model.
4. Add tool and retry costs.
5. Multiply by runs per month.
6. Find the largest line and attack it first.

Read the tokens from the usage fields, not from estimates.

## Reliability checklist

| Risk | Control |
|---|---|
| Rate limit or overload error | Retry with backoff and a cap |
| A slow call | Timeout and streaming |
| Duplicate side effects | Idempotent operations |
| A model becomes unavailable | Fallback model and pinned versions |
| Runaway spend | Spend limits and session budgets |
| One team starves another | Separate workspaces with limits |

Test each control by simulating the failure.

## Upgrade a model

1. Read the model's migration guide.
2. Set effort explicitly.
3. Remove settings it rejects, such as fixed thinking budgets.
4. Replace forced tool choice with auto plus strict tool use.
5. Rerun the evals and compare cost and latency.
6. Switch behind a flag, with a rollback.

Check each model's lifecycle every month.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Optimising by guess | You may attack a small line | Measure cost per feature |
| Choosing the smallest model by name | Quality may drop | Test it on the eval |
| Retrying forever | It amplifies an outage | Cap retries and back off |
| Upgrading without the eval | Defaults and settings change | Follow the migration guide and rerun |

## Cheat sheet

**Know**
- Measure cost per run first.
- Free wins before trade-offs.
- Batch is half price for work nobody waits on.
- Upgrade by migration guide and eval.

**Do**
- Build the cost model.
- Apply one free win and one trade-off and report.
- Test retry and timeout.
- Write the upgrade go or no-go.

## Exercises

1. Build a cost model for one workflow: tokens per run by type, cost per run, runs per month and monthly cost. Find the largest line.
2. Apply one free win and one trade-off. Rerun the eval and report quality, cost and latency before and after.
3. Add retry with backoff and a timeout. Simulate a rate-limit error and show that the system recovers without duplicating side effects.
4. Run a model upgrade: read its migration guide, change the required settings, rerun the eval and write the go or no-go.

## Vocabulary

| Term | Meaning |
|---|---|

| Trade-off | A saving that changes quality or speed, so it needs an eval. |

## Going further

- Rate-limit tiers are Start, Build and Scale. Limits are requests, input tokens and output tokens per minute, and workspaces can be capped lower.
- The Rate Limits API and the Usage and Cost Analytics API let you audit headroom and spend from code.
- Managed Agents sessions can carry a hard spend budget, and the Console session viewer shows cost over time.
- In Claude Code, a managed setting can cap effort for every model. That is a cost and governance lever.
