# Session 24: Expert capstone: ship, drill, teach

Level 5: Expert (beyond 100). Deliverable: A production system, runbook, postmortem and a taught session. Worth: pass or fail, no points. This is a gate.

Contents: Goal and outcomes, Key points, Plain-language glossary, Production-ready checklist, The runbook, The failure drill, The postmortem, Teach and lead, Worked demo: ship, drill, teach, Common mistakes, Cheat sheet, Exercises, Case to attempt, Vocabulary, Score ladder (what your work looks like at each level), Going further, Study sources, Self-check questions, Exit ticket.

## Goal and outcomes

**Goal.** The learner ships a production-ready system with eval, tracing, cost, security and a runbook, survives a failure drill and teaches the stack to someone else.

**You will be able to:**
- Deliver a production system with its eval suite, tracing, cost model and security review
- Write a runbook, then find, contain and fix a live failure and write the postmortem
- Lead adoption: teach one session of the course and write a team rollout plan

## Key points

- The capstone is a system of the learner's choice that uses at least four Level 5 skills: context and caching, effort and schemas, evals and tracing, an orchestrated or MCP build, security controls, cost and reliability engineering.
- Production-ready means evidence in six areas: an eval suite whose held-out score gates every change; tracing and a cost per run; enforced security controls and an injection test; limits, retries, a fallback and a rollback; a cost model; and a named owner.
- The runbook lets an on-call person who is not the author run, monitor and fix the system: dashboards and alerts, common failures with detection and fix, rollback, escalation and the model-upgrade procedure.
- The failure drill. The examiner breaks something live: a model change, a tool outage, an injected document or a rate limit. The learner finds it in the traces, contains it, fixes or rolls back, verifies with the eval and writes a blameless postmortem: timeline, cause, what worked, what failed, actions and the new test.
- Experts teach. The learner teaches one session of the course to a colleague, writes the rollout plan for a team and lists the next three skills. The monthly routine continues: release notes, model lifecycles, evals and permissions.

## Production-ready checklist

| Area | Evidence |
|---|---|
| Eval | A suite with a held-out score that gates every change |
| Observability | Traces, cost per run and alerts |
| Security | Enforced controls and an injection test |
| Reliability | Limits, retries, a fallback and a tested rollback |
| Cost | A cost model and a monthly estimate |
| Ownership | A named owner and a runbook |

No row without evidence.

## The runbook

1. What the system does and who owns it.
2. Dashboards and alerts.
3. Common failures, each with detection and fix.
4. Rollback steps.
5. Escalation contacts.
6. The model-upgrade procedure.
7. How to update the runbook.

Someone other than the author must be able to run it.

## The failure drill

1. The examiner breaks something live.
2. Detect it from alerts or traces.
3. Contain the damage.
4. Fix it or roll back.
5. Verify with the eval.
6. Write the postmortem and add a test.

Contain first, then fix.

## The postmortem

| Section | Contents |
|---|---|
| Timeline | What happened and when |
| Cause | The root cause, not the symptom |
| Went well | Which detection and controls worked |
| Went badly | The gaps |
| Actions | Owned fixes with dates |
| New test | The case added to the suite |

Blameless: fix the system.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Building before criteria | Nothing to judge against | Write criteria first |
| A runbook only the author can follow | It fails at 3 a.m. | Have someone else run from it |
| No rollback | A bad upgrade stays live | Pin versions and rehearse the rollback |
| A postmortem that blames | It hides the real cause | Fix the system and add a test |

4. Teach one session of the course to a colleague, write the team rollout plan and list the next three skills to build.

## Going further

- Subscribe to release notes and lifecycle changes. Run the monthly routine and rerun the evals on every model change.
- Re-question every workaround as models improve. Anthropic found that harness assumptions go stale and some fixes became dead weight.
- Publish a short design note on what you built. Review by others makes the next system better.
- Self-assess against the Level 5 rungs and pick one area to deepen next.
