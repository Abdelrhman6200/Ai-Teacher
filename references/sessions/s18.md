## Goal and outcomes

**Goal.** The learner controls how much Claude thinks, forces machine-readable output and designs tools that an agent picks and uses correctly.

**You will be able to:**
- Set effort and max_tokens for a task from measured results, not from defaults
- Return guaranteed-valid JSON with structured outputs or strict tool use
- Write tool definitions and a tool set that an agent selects correctly

## Key points

- Adaptive thinking. Claude decides for each request whether to think. Control it with the effort setting (low, medium, high, xhigh, max) in output_config.effort. Effort is soft guidance, not a budget, and defaults differ by model, so set it explicitly.
- Fixed thinking budgets are gone. budget_tokens and thinking type enabled return an error on the newest models. max_tokens is the hard ceiling for thinking plus answer: raise it if reasoning was needed, or lower effort if the task was over-thought.
- Steer in order: set effort first, then add system prompt guidance only if triggering still does not fit, then per-message hints. Changing effort between requests can invalidate the prompt cache, so hold it constant inside a conversation.
- Structured outputs use constrained decoding to guarantee schema-valid JSON (output_config.format) and valid tool inputs (strict: true). Use them for anything a program parses. Forced tool choice (any or tool) now returns an error on several models: use auto with strict tool use.
- A tool is a contract with an agent. The description matters most: what it does, when to use it and when not to, what each parameter means, what it returns. Prefix names by service, return only high-signal fields, and keep the set small and non-overlapping.

## Plain-language glossary

| Term | Meaning | Think of it as |
|---|---|---|
| Effort | A soft dial for how much Claude thinks | A volume knob |

| Structured output | Output forced to match a schema | A form with required boxes |
| Tool description | The text an agent reads to pick a tool | The label on a drawer |

## Effort levels

| Level | Behaviour | Use for |
|---|---|---|
| low | Minimises thinking, skips it on simple tasks | Lookups, routing |
| medium | Moderate thinking, may skip it on simple queries | Everyday work |
| high | Thinks on most requests that benefit | Complex reasoning |
| xhigh | More readily and deeper than high | Extended exploration |
| max | Deepest, no limit on thinking length | The hardest problems |

Availability and the default differ by model. Set effort explicitly.

## Steer thinking in this order

1. Set the effort level.
2. Add system prompt guidance only if triggering still does not fit.
3. Add per-message hints in the user turn.
4. Cap the total with max_tokens.
5. Measure thinking tokens, latency and quality on real traffic.

On some models, prompts to think less are unreliable. Lower the effort instead.

## Structured output options

| Option | Guarantees | Set with |
|---|---|---|
| JSON outputs | The response matches your JSON schema | output_config.format |
| Strict tool use | Tool names and inputs match the schema | strict: true on the tool |
| Both together | Valid tool inputs and a valid final answer | Both in one request |

Forced tool choice (any or tool) returns an error on several models. Use auto with strict tool use.

Anything a program parses should be schema-enforced, not requested in prose.

## A good tool definition

| Part | Write |
|---|---|
| Name | Prefixed by service, such as github_list_prs |
| Description | What it does, when to use it, when not to, what it returns |
| Parameters | Each one explained, with its effect |
| Output | Only the high-signal fields, not raw dumps |
| Examples | Optional input examples for hard cases |

The description is the largest single lever on tool performance.

## Tool set design rules

- Few tools that cover natural subdivisions of the task.
- No two tools with overlapping purpose.
- Many tools: load definitions on demand with tool search.
- Chains of small calls: run them as one script with programmatic tool calling.
- Evaluate on real tasks and read the transcripts.

A smaller, clearer set is chosen more reliably.

## Worked demo: measure effort and sharpen a tool

Run this yourself on your own material.

| Step | Do this | What it shows |
|---|---|---|
| 1 | Choose one hard reasoning task and one simple lookup | Both go through all three levels |
| 2 | Run each at low, medium and high and record quality, tokens and latency | The lookup gains nothing from high |
| 3 | Define a schema and call with output_config.format | The reply parses every time |
| 4 | Swap a vague tool description for a complete one and rerun five requests | Tool choice becomes correct |

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| High effort everywhere | Latency and cost on easy work | Set effort per task from tests |
| A fixed thinking budget | Rejected on the newest models | Use effort and max_tokens |
| Asking for JSON in prose | The output can still be malformed | Enforce a schema |
| Vague tool descriptions | The agent has to guess | State what, when, when not, returns |

## Cheat sheet

**Know**
- Effort is a soft dial. Set it first, per task.
- max_tokens is the hard ceiling for thinking plus answer.
- Schema-enforce anything a program parses.
- The tool description is the biggest lever on tool choice.

**Do**
- Test low, medium and high on one task and tabulate.
- Enforce a schema on an extractor.
- Rewrite a vague tool description and retest.
- Merge overlapping tools and rerun.

## Exercises

1. Run one reasoning-heavy task and one simple lookup at low, medium and high effort. Record answer quality, output tokens and latency in a table.
2. Define a JSON schema for an extraction task and enforce it with structured outputs. Feed it ten messy inputs and count parse failures.
3. Write two versions of a tool description, one vague and one complete. Give the agent five requests and record which tool it picks each time.
4. Merge or rename overlapping tools in a set of six and rerun the five requests.

## Going further

- Programmatic tool calling lets Claude run a chain of tool calls as one script in a sandbox, so intermediate results never enter the context. Tools with strict: true are not supported with it.
- Anthropic reports that presenting MCP servers as code APIs cut one example from about 150,000 to about 2,000 tokens.
- The advisor tool lets a faster executor model consult a more capable advisor mid-generation for a plan or a correction.
- Model migrations change defaults. The Opus 5.5 guide says to set effort explicitly, drop old thinking settings and replace forced tool choice with auto plus strict tools.
