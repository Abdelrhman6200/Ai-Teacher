# Session 15: Evals, safety and cost

Level 4: Operator (75 to 100). Deliverable: A 20-case eval, an injection test log and a cost note. Worth: 5 points.

Contents: Goal and outcomes, Key points, Plain-language glossary, From criteria to tests, A 20-case eval, Three ways to grade, An injection test, A cost note, Worked demo: a 20-case eval, Common mistakes, Cheat sheet, Exercises, Case to attempt, Vocabulary, Score ladder (what your work looks like at each level), Going further, Study sources, Self-check questions, Exit ticket.

## Goal and outcomes

**Goal.** The learner proves the agent works, limits what it can break and knows what it costs.

**You will be able to:**
- Write measurable success criteria and a 20-case eval with edge cases
- Choose a grading method: code, LLM or human
- Run an injection and permission test and add deterministic guardrails
- Estimate and cap cost, and compare models on the eval

## Key points

- Good success criteria are specific, measurable, achievable and relevant. Most use cases need several: accuracy, consistency, tone, privacy, latency and price.
- Evals should mirror the real task and include edge cases such as empty or overlong input, harmful input, ambiguous cases and topic shifts. Automate grading where possible and favour volume over a few hand-graded cases.
- Grading: code-based is fastest and most reliable but limited in nuance; LLM-based is flexible, so test its reliability first, write a detailed rubric with automatic-fail conditions, ask for a clear verdict or a 1 to 5 score, enable thinking on the grader and use a different model from the one being graded; human grading is highest quality but slow and costly.
- Workflow: define criteria, write cases including edge cases, write a first prompt, test, refine, and check against held-out cases before shipping.
- Advice versus enforcement: prompts, CLAUDE.md and skills are advice; hooks, deny rules, the sandbox and managed settings are enforced. Cost and time can be capped with limits such as --max-turns and --max-budget-usd, and a person approving the merge has the last word.
- Text from connectors and the web can carry instructions. Treat it as data and keep write and send tools behind approval.
- Cost levers: choose the tier, tune effort before switching model, use fast mode where speed matters (up to 2.5 times output speed at premium pricing on supported models), route bulk work to cheaper models and disable unused MCP servers. Subagent requests count toward usage.

## Plain-language glossary

| Term | Meaning | Think of it as |
|---|---|---|
| Eval | A set of test cases with expected results | An exam for your workflow |
| Grader | Code, another model or a person that scores outputs | The examiner |
| Guardrail | A control that limits what can go wrong | A fence |
| Injection | Hidden instructions in text the agent reads | A forged note in the in-tray |
| Cost per run | Tokens in and out at the model's price, times runs per month | The unit price |

## From criteria to tests

| Criterion | A measurable version |
|---|---|
| Accuracy | 95% of extracted fields match the source |
| Consistency | Same format in 20 of 20 runs |
| Tone | A rubric score of 4 or more out of 5 |
| Privacy | No personal data in any output |
| Latency | Under 3 seconds |
| Price | Under $0.01 per run |

The numbers are examples. The learner sets their own.

## A 20-case eval

- 12 typical cases from real use.
- 5 edge cases: empty input, overlong input, harmful input, ambiguous case, topic shift.
- 3 adversarial cases: an instruction hidden in a document, in a tool result, a request to break a rule.
- Each case has an expected result.
- Grade with code wherever possible.

Volume over a few hand-graded cases.

## Three ways to grade

| Method | Strength | Limit |
|---|---|---|
| Code | Fastest and most reliable | Little nuance |
| LLM | Flexible and scales | Test its reliability first |
| Human | Highest quality | Slow and costly |

LLM grader: a detailed rubric with automatic-fail conditions, a clear verdict or a 1 to 5 score, thinking on, and a different model from the one graded.

Match the method to the criterion.

## An injection test

1. Plant an instruction in a test document.
2. Plant one in a tool result.
3. Run the agent on both.
4. Record what it did and what stopped it.
5. Add a guardrail: a permission, a hook or an approval.
6. Rerun and compare.

Test accounts and non-sensitive data only.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Judging from a few examples | Small samples hide failures | Favour volume with automated grading |
| A model grading its own output | It tends to agree with itself | Use a different grader model and a detailed rubric |
| A guardrail written as a prompt line | Advice can be ignored | Enforce with a permission, hook, sandbox or approval |
| Estimating cost by feel | Volume turns small costs into surprises | Cost per run times runs per month at two models |

## Cheat sheet

**Know**
- Criteria: specific, measurable, achievable, relevant.
- Eval: typical, edge and adversarial cases.
- Grade by code first, then an LLM with a rubric, then a person.
- Prompts advise. Hooks and deny rules enforce.

**Do**
- Write criteria and 20 cases.
- Grade and compare two models or effort levels.
- Red-team with an injection and add a guardrail.
- Write the cost note.

## Exercises

1. Build a 20-case eval for the session 14 agent or a session 9 skill: 12 typical, 5 edge and 3 adversarial cases, each with an expected result. Grade with code wherever possible.

3. Red-team: attempt injection through a document and through a tool result. Add one guardrail (a permission, a hook or an approval) and rerun.
