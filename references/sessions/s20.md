## Goal and outcomes

**Goal.** The learner chooses between a workflow and an agent, designs a multi-agent system with enforced limits, and runs long work across context windows.

**You will be able to:**
- Choose the simplest pattern that passes the eval: single call, workflow or agent
- Design an orchestrator with sub-agents, each with its own permissions and budget
- Run long-horizon work with a progress file, checkpoints and a handoff

## Key points

- Simplest first. Workflows follow fixed code paths. Agents choose their own steps. Use an agent only when the steps cannot be known in advance. The common patterns are prompt chaining, routing, parallelization (sectioning or voting), orchestrator-workers and evaluator-optimizer.
- Multi-agent pays off on broad, parallel work. Sub-agents search in their own contexts and return compressed findings. They use far more tokens, so keep them for high-value tasks. In Anthropic's research system, token use alone explained about 80 percent of performance variance on a browsing benchmark.
- Enforce limits, do not request them. In the Agent SDK use allowed and disallowed tools, permission modes, hooks (PreToolUse, PostToolUse, Stop, SubagentStart, SubagentStop and others) and budgets such as maximum turns and maximum spend. Deny wins. Sub-agents do not inherit the parent's permissions.
- Managed Agents is a hosted harness. An agent is a versioned configuration (model, system prompt, tools, MCP servers, skills). An environment is a container template. A session is a running agent in its own sandbox with an event log. Use it for long or asynchronous tasks, and the Messages API when you need your own loop.
- Long-horizon work needs handoffs. An initializer run sets up the environment, then each run makes one increment and leaves a progress file, a feature list and git history for the next window. Tests keep agents on track. Re-question harness workarounds as models improve.

## Plain-language glossary

| Term | Meaning | Think of it as |
|---|---|---|
| Workflow | A fixed code path with model calls inside | A train on rails |
| Agent | The model chooses its own steps and tools | A taxi driver choosing the route |
| Orchestrator | An agent that splits work and delegates it | A site manager |
| Handoff | State written to files for the next session | A shift-change note |

## Patterns

| Pattern | Use when |
|---|---|
| Prompt chaining | Fixed steps, each feeding the next |
| Routing | Different inputs need different handlers |
| Parallelization | Independent parts (sectioning) or several views (voting) |
| Orchestrator-workers | Steps cannot be predicted: a lead delegates |
| Evaluator-optimizer | A clear quality bar and iterative refinement |

Start with a single call. Add structure only when the eval shows it helps.

## Advice or enforced

| Mechanism | Kind |
|---|---|
| A line in the prompt | Advice |
| Allowed and disallowed tools | Enforced |
| A hook that blocks a call | Enforced |
| Permission mode and deny rules | Enforced |
| A budget: maximum turns or spend | Enforced |

If a failure would be costly, use an enforced mechanism.

## Managed Agents objects

| Object | What it is |
|---|---|
| Agent | Versioned configuration: model, system prompt, tools, MCP servers, skills |
| Environment | Container template: networking and packages |
| Session | A running agent in its own sandbox, with an event log |
| Events | Messages between your application and the agent |

Cloud sandboxes by default. Self-hosted sandboxes keep tool execution on your infrastructure.

## A long-running handoff

1. An initializer run sets up the environment and a feature list.
2. Each run does one increment.
3. It writes a progress file and commits to git.
4. The next run reads the progress file and the log first.
5. Tests decide when a feature is done.

Context resets use a structured handoff, not a hope.

## Trade-offs of multi-agent systems

- Far more tokens than a single agent.
- Coordination errors: duplicate work and gaps.
- Sub-agents need precise task descriptions.
- Each sub-agent needs its own permissions.
- Worth it for broad, parallel, high-value work.

Measure quality and cost against a single agent before you adopt it.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Agents for fixed problems | Cost and error with no gain | Use a workflow |
| Limits written in the prompt | A prompt is advice | Use hooks, deny rules and budgets |
| Sub-agents with full tool access | They do not inherit limits, so each needs its own | Scope each one |
| No state on disk | A reset loses the plan | Keep a progress file and git history |

## Cheat sheet

**Know**
- Use the simplest pattern that passes the eval.
- Prompts advise. Hooks, deny rules and budgets enforce.
- Sub-agents do not inherit permissions.
- Long work needs a progress file, git history and a structured handoff.

**Do**
- Classify three tasks.
- Design an orchestrator and two scoped sub-agents.
- Prove one hook blocks an action.
- Run a handoff across two sessions.

## Exercises

1. For three of your tasks decide single call, workflow or agent and write one line why. Build the cheapest option that passes your eval.
2. Design an orchestrator with two sub-agents. For each write its tools, permissions, budget and the summary it must return.
3. Add one enforced guard, a hook or a deny rule that blocks one action. Prove it blocks that action.
4. Run a task that overflows one window. Keep a progress file and hand off to a fresh session. Check that it resumes correctly.

## Going further

- Evaluator-optimizer: one model generates and another grades against criteria. Anthropic's long-running app work used a generator and an evaluator with concrete, gradable criteria.
- Managed Agents separates the agent loop, the session log and the sandbox so each can change without breaking the others. A workaround added for an older model can become dead weight on a newer one.
- Checkpointing lets you rewind file changes an agent made. The Agent SDK supports file checkpointing and session resume.
- Anthropic's agent-team compiler write-up found that tests were what kept parallel agents on track.
