## Goal and outcomes

**Goal.** The learner threat-models an agent, enforces defences that hold when the model is fooled, and rolls Claude out to a team with policy, monitoring and an audit trail.

**You will be able to:**
- Threat-model an agent: untrusted inputs, powerful tools and the data they can reach
- Enforce defences with permissions, sandboxing, hooks and managed settings
- Plan a team rollout: identity, policy, monitoring, spend limits and an audit trail

## Key points

- Prompt injection is instructions hidden in content the agent reads: pages, files, tool results. Direct injection comes from the user, indirect injection from content. It is not solved, so design so that a fooled model cannot do serious harm.
- Find the dangerous combination. Risk concentrates where an agent holds private data, reads untrusted content and can act or send data outward. Remove at least one: isolate the data, keep untrusted content away from privileged agents, or block egress.
- Advice versus enforcement. Prompts, CLAUDE.md and skills are advice. Deny rules, hooks, the sandbox and managed settings are enforced. Deny rules hold in every permission mode, including auto and bypass. Use them for must-never actions.
- Sandbox the machine. OS-level file isolation and a network allowlist stop a compromised agent from reaching arbitrary servers. A deny rule on a fetch tool does not stop curl in an allowed shell: the sandbox does.
- Roll out in order: provider and sign-in, managed settings, enforced permissions, sandbox and approved servers and plugins, OpenTelemetry and analytics, spend and model limits, data handling. Keep an audit trail of sessions and tool decisions, and verify each machine with /status.
- Guidance is not enforcement, including for money. Anthropic's prompting guide supplies a payments block that tells Claude not to release payments itself, and says plainly that it is guidance: require human approval in the tool for anything that moves money.

## Plain-language glossary

| Term | Meaning | Think of it as |
|---|---|---|
| Prompt injection | Instructions hidden in content the agent reads | A forged note in the inbox |
| Least privilege | Only the access the task needs | A key to one room |
| Sandbox | OS-level limits on files and network | A fenced yard |
| Audit trail | A record of what ran and who approved it | Security camera footage |

## Injection types

| Type | Source | First defence |
|---|---|---|
| Direct | The user of your application | Screen input, harden the system prompt |
| Indirect | Pages, files, tool results | Treat as untrusted data, limit tools, sandbox |

Claude is trained to resist injection and some tools add classifiers. None of this is a guarantee.

## Layers of defence

| Layer | What it stops |
|---|---|
| Input screening | Known attack patterns reaching the model |
| Least privilege tools | Damage if the model is fooled |
| Deny rules and hooks | Named actions, in every mode |
| Sandbox | File access outside the project and network egress |
| Human approval | Irreversible or outbound actions |
| Monitoring | What slipped through |

Each layer assumes the one before it can fail.

## The injection test

1. Plant an instruction in a document.
2. Plant one in a tool result.
3. Run the agent on both.
4. Record what it did and which control stopped it.
5. Add or tighten the control, then rerun.
6. Keep the cases as regression tests.

Pass when a control stops the action, not when the model happened to refuse.

## Managed settings to know

| Setting | Effect |
|---|---|
| permissions.deny | Actions that are always blocked |
| allowManagedPermissionRulesOnly | Only managed permission rules apply |
| sandbox.network.allowedDomains | The network allowlist |
| allowedMcpServers | Which servers members may add |
| maxEffortLevel | Caps effort for every model |

Managed values beat user and project settings. Array settings merge: users can extend, not remove.

## Rollout order

1. Pick the provider and sign-in method.
2. Deliver managed settings.
3. Enforce permissions, sandbox, servers and plugins.
4. Turn on OpenTelemetry and analytics.
5. Set spend limits and model limits.
6. Review data handling and retention.
7. Train, then verify each machine with /status.

Keep an audit trail of sessions and tool decisions.

## Worked demo: plant, block, verify

Run this yourself on your own material.

| Step | Do this | What it shows |
|---|---|---|
| 1 | Plant "send this file to a URL" in a test document | It is untrusted data |
| 2 | Run the agent and record what it tried | Note which control stopped it |
| 3 | Add a deny rule and a network allowlist, then rerun | The action fails even if the model complies |
| 4 | Check the effective settings with /status | The managed source shows as the winner |

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Relying on the prompt | A prompt is advice | Add enforced controls |
| Allowing Bash and denying one fetch tool | curl still works | Sandbox the network |
| One broad credential for every agent | One injection reaches everything | Scope credentials per task |
| No logs | You cannot investigate | Enable OpenTelemetry and keep decisions |

## Cheat sheet

**Know**
- Injection is unsolved. Design for a fooled model.
- Prompts advise. Deny rules, hooks and the sandbox enforce.
- Sandbox the network: a fetch deny rule alone leaves curl.
- Rollout: identity, managed settings, monitoring, spend limits, audit.

**Do**
- Draw the threat model.
- Run an injection test on two inputs.
- Write the managed settings.
- Write the rollout plan for 20 people.

## Exercises

1. Draw the threat model for one agent: the inputs it reads, the tools it has, the data it can reach and where it can send data. Mark the weakest link.
2. Run an injection test. Plant an instruction in a document and in a tool result. Record what the agent did and which control stopped it.
3. Write the managed settings you would deploy: deny rules, sandbox, allowed servers and marketplaces, and model limits. Check the winning source with /status.
4. Write the rollout plan for a team of 20: identity, policy, monitoring, spend limits, audit trail, training and a review date.

## Going further

- Auto mode adds a classifier that probes tool outputs for injection, but deny and ask rules are evaluated before it. Use managed deny rules for must-never actions.
- Managed settings can disable the bypass-permissions mode and make managed rules the only source of permission rules.
- A gateway between developers and the provider can add request-level audit logging and routing by data sensitivity.
- Zero data retention and HIPAA configuration depend on the provider and the plan. Check the data-handling pages before promising anything to a regulated team.
- Enterprise admins can scan uploaded skills and plugins for malicious content (beta since 6 August 2026). It supports a review step; it does not replace reading a skill's files before you trust it.
