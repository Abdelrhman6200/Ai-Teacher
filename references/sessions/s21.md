## Goal and outcomes

**Goal.** The learner builds a secure MCP server, packages skills and a plugin for a team, and evaluates them before release.

**You will be able to:**
- Build an MCP server with tools, resources and prompts over the right transport
- Secure it: token validation, minimum scopes, no token passthrough and a tested rejection
- Package, evaluate and version skills and a plugin for team distribution

## Key points

- MCP servers expose tools (actions), resources (data) and prompts (templates). Use stdio for a local process and Streamable HTTP for a remote server. The older HTTP with SSE transport is deprecated.
- Design for the agent. Offer few, well-named tools with token-efficient outputs and clear errors. Keep read tools separate from write tools so approvals can target the writes, and mark tools with no side effects as read-only.
- Authorize properly. A remote server is a resource server: it validates access tokens issued for it, checks the audience, accepts access tokens only and never issues tokens. It must not forward a client's token to another service. A local stdio server takes credentials from the environment. Ask for the minimum scopes.
- Skills package instructions, scripts and resources that load only when relevant. Before release, evaluate triggering accuracy, isolation, coexistence with other skills and instruction following. Write the evaluations before the long instructions.
- Plugins bundle skills, connectors, agents and hooks for a team. Distribute them through a marketplace, version them, and use managed settings to restrict which marketplaces and servers members may add. Review a plugin like code, because it can ship hooks and servers that run code.

| Primitive | What it is | Example |
|---|---|---|
| Tool | An action the model can call | create_ticket |

Most servers need tools only. Add resources and prompts when they help.

## Transports

| Transport | Use | Credentials |
|---|---|---|
| stdio | A local process on the user's machine | From the environment |
| Streamable HTTP | A remote, shared server | Bearer tokens (OAuth) |
| HTTP with SSE | Deprecated | Migrate |

Remote servers also validate the Origin header to resist DNS rebinding.

## Secure a remote server

1. Require a bearer token on every request.
2. Validate signature, expiry, issuer and audience.
3. Accept access tokens only, never ID tokens.
4. Request and check the minimum scopes.
5. Call other services with the server's own credentials, never the client's token.
6. Log every call with the user identity.

Test the rejection of a token issued for a different audience.

## Evaluate a skill before release

| Dimension | Question |
|---|---|
| Triggering | Does it activate for the right requests and stay quiet otherwise? |
| Isolation | Does it work on its own? |
| Coexistence | Does it steal triggers from other skills? |
| Instruction following | Does Claude follow its steps? |

Write these evaluations before the long instructions.

## Admin controls for plugins and servers

| Control | Setting |

| Where skills, agents and hooks may come from | strictPluginOnlyCustomization |

Managed settings override user settings. Check names on the live settings page.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Passing the user's token downstream | It breaks the trust boundary | Use the server's own credentials |
| Accepting any valid token | It may belong to another service | Check the audience |
| Broad scopes | One leak exposes everything | Request the minimum |
| Shipping a plugin unreviewed | It can run code | Review it and allowlist the source |

## Cheat sheet

**Know**
- Tools act, resources inform, prompts are templates.
- stdio is local. Streamable HTTP is remote.
- Validate the token audience. Never pass the token on.
- Evaluate skills for triggering, isolation, coexistence and following.

**Do**
- Build a server with two read tools and one write tool.
- Reject a wrong-audience token.
- Write skill evaluations first.
- Package, version and write the rollback.

## Exercises

1. Build a small MCP server with two read tools and one write tool. Test it from Claude, and read each description as the agent would.
2. Add token authentication to the HTTP version. Reject a request with no token and one whose token was issued for a different audience, and show both rejections.
3. Write a skill and three evaluation scenarios first. Measure triggering with and without the skill, and check it does not steal triggers from another skill.
4. Package two skills and the server into a plugin. Version it and write the install and rollback steps.

## Going further

- Enterprise-managed authorization lets the company identity provider decide which MCP servers an employee may use and revoke access in one place.
- Claude Enterprise can scan custom skills for hidden code execution, data transfer and attempts to tamper with safeguards. A skill that fails the scan is blocked.
- Code execution with MCP presents servers as code APIs that the agent explores on a file system, which cut one example from about 150,000 to about 2,000 tokens.
- The MCP specification is versioned by date. State which version your server targets and recheck it each quarter.
