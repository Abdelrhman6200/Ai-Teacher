# Session 11: Claude inside workflows

Level 3: Builder (50 to 75). Deliverable: The workflow running on a schedule, with the skills of session 9 and the plugin of session 10. Worth: 7 points. This is a gate.

## Goal and outcomes

**Goal.** The learner puts Claude into a no-code or low-code workflow with routing, validation and approval, and has made one API call by hand.

**You will be able to:**
- Make an API call and read its parts: model ID, max tokens, messages, effort
- Design a workflow: trigger, classify, draft, human check, act, log
- Validate structured output and handle bad output
- Place human approval before anything that sends or writes

## Key points

- The Client SDK calls the API directly; you write the tool loop or use the tool runner. Current model IDs: claude-fable-5-2, claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5.
- Effort is set with adaptive thinking and an effort value in the request's output configuration.
- Prompt chaining is a named technique: split a task into steps so each step gets one clear instruction.
- Split by difficulty. Use the cheapest tier for classification, extraction and routing, and a stronger tier for drafting and analysis.
- Ask for a fixed format, validate it before the next step, retry once, then route to a human.
- Put approval before every send or write, and log time, model, input, output and approver for each run.
- Any workflow tool with an HTTP step or a Claude node can do this. Node names vary, so read the tool's own documentation.

## Plain-language glossary

| Term | Meaning | Think of it as |
|---|---|---|
| API | A way for software to send Claude a request and get an answer | Ordering through a hatch instead of a chat |
| Workflow | A fixed sequence of steps with Claude in some of them | A production line |
| Prompt chain | Each step gets one clear instruction and feeds the next | A relay race |
| Validation | Checking the output has the shape the next step expects | Quality control at the door |
| Approval gate | A person decides before anything sends or writes | A countersignature |

## The parts of an API call

- Model ID: for example claude-haiku-5-5 or claude-sonnet-5-5
- Maximum output tokens
- Messages: the conversation, each with a role and content
- Effort: adaptive thinking plus an effort value in the output configuration
- Response: the text Claude wrote and the tokens used

Make one call by hand with Haiku 5.5, then Sonnet 5.5, and compare.

## The workflow shape

1. Trigger: a form arrives.
2. Classify: Haiku 5.5 sorts it.
3. Draft: Sonnet 5.5 writes the reply.
4. Check: a person approves.
5. Act: send or save.
6. Log: one row per run.

Cheapest tier for classification, a stronger tier for drafting.

## When the output is bad

1. Ask for a fixed format, for example named fields.
2. Validate it before the next step.
3. Retry once.
4. Route to a human.
5. Log the failure with its input.

Use the five bad inputs of the live task to trigger each branch.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| One huge prompt for the whole job | Hard to test and hard to fix | Chain small steps, one instruction each |
| The top model at every step | Cost and time add up | Split by difficulty |
| Trusting free-text output | The next step breaks on a missing field | Ask for a fixed format, validate, retry once, route to a person |
| No log | A wrong output cannot be explained later | Write one row per run |

## Cheat sheet

**Know**
- An API call has a model ID, max tokens, messages and effort.
- Chain small steps. The cheapest tier classifies.
- Fixed format, validate, retry once, then a person.
- Approve before any send. Log every run.

**Do**
- Trigger the flow.
- Classify with Haiku 5.5 and draft with Sonnet 5.5.
- A person approves, then send.
- Log time, model, input, output and approver.

## Exercises

1. One API call by hand with Haiku 5.5, then Sonnet 5.5. Inspect the response and change the effort.
2. Build a four-step workflow on a real job: trigger, Haiku classify, Sonnet draft, human approve, then send or save. Include a branch for invalid output.
3. Break it with 5 bad inputs: empty, very long, wrong language, malformed and hostile. Record what happens.
4. Add a log row per run: time, model, input id, output, approver.
