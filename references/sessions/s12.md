# Session 12: Claude Code fundamentals

Level 4: Operator (75 to 100). Deliverable: A small project shipped with tests and a CLAUDE.md. Worth: 5 points.

Contents: Goal and outcomes, Key points, Plain-language glossary, First run, What goes in CLAUDE.md, A specific prompt, Checks Claude can run, Spec interview, Worked demo: ship a small tool, Common mistakes, Cheat sheet, Exercises, Case to attempt, Vocabulary, Score ladder (what your work looks like at each level), Going further, Study sources, Self-check questions, Exit ticket.

## Goal and outcomes

**Goal.** The learner ships a small real project with Claude Code, with a check Claude can run on its own work.

**You will be able to:**
- Install Claude Code on one surface and run a first task
- Write a short CLAUDE.md that holds only what Claude cannot see
- Give Claude a pass or fail check and ask for evidence
- Plan first, then build, and keep context under control

## Key points

- Claude Code is an agentic coding tool that reads a codebase, edits files, runs commands and connects to development tools. It runs in the terminal, VS Code, JetBrains, the desktop app and the web, and needs a Claude subscription or Console account.
- Install natively, check with claude --version, then run claude inside a project folder and sign in.
- The defaults already do a lot: new terminal sessions start in auto mode, where a classifier reviews risky actions; Claude delegates to subagents; long conversations are compacted automatically.
- Tell Claude what it cannot see. Test before writing anything down: could it find this by reading the code, and would it actually look? If both are yes, leave it out. A specific prompt names the file, the symptom and what fixed looks like.
- CLAUDE.md loads into every session, so keep it short: the commands that verify work, places where the code misleads, decisions made outside the repo, and anything you have corrected twice. The docs recommend staying under 200 lines. /init drafts one, /context confirms it loaded, and personal preferences go in CLAUDE.local.md.
- Claude stops when work looks done. Give it a check that returns pass or fail (tests, a build exit code, a linter, a diff against a fixture) and ask for the command and its output as evidence.
- When you do not know what you want yet, ask Claude to interview you and write SPEC.md, then build from it in a fresh session.

## What goes in CLAUDE.md

| Keep | Leave out |
|---|---|
| The commands that verify work | Anything Claude finds by reading the code |
| Places where the code misleads | File-by-file descriptions |
| Decisions made outside the repo | Conventions it already knows |
| Anything you have corrected twice | Long explanations |

Stay under 200 lines. /init drafts one, /context confirms it loaded, CLAUDE.local.md holds personal preferences.

Test each line: could it find this by reading the code, and would it actually look?

## A specific prompt

| Version | Prompt |
|---|---|
| Vague | Fix the login bug. |
| Specific | Users are logged out after 10 minutes. The session code is in auth/session.js. Fixed means tests/session.test.js passes and a session survives 30 minutes. Run the test and show me the output. |

Name the file, the symptom and what fixed looks like.

## Checks Claude can run

| Check | Passes when |
|---|---|
| Tests | They exit with code 0 |
| Build | It exits with code 0 |
| Linter | No errors |
| Diff against a fixture | No differences |

Ask for the command and its output as evidence.

Claude stops when the work looks done. A pass or fail check moves the line.

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Writing everything into CLAUDE.md | It loads in every session | Keep only what Claude cannot see |
| A vague task | Claude guesses | Name the file, the symptom and what fixed looks like |
| No check | Done only looks done | Give a test and ask for the command and its output |
| An absolute rule left in CLAUDE.md | Advice can be ignored | Move it to a hook or deny rule (session 13) |

## Cheat sheet

**Know**
- CLAUDE.md holds only what Claude cannot see, under 200 lines.
- A specific prompt names the file, the symptom and what fixed looks like.
- Give a pass or fail check and ask for the command and its output.
- Not sure what you want? Interview into SPEC.md.

**Do**
- Install and run a first task.
- Interview into SPEC.md, then build in a fresh session.
- Build with a test and ask for evidence.
- Audit CLAUDE.md with /init and /context.

## Exercises

1. Install, then build a small command-line tool, a script, a site or a data-cleanup job in an empty folder, with a test.
2. Spec interview. Have Claude interview you into SPEC.md, then start a fresh session and build from it.
3. CLAUDE.md audit. Run /init, delete every line Claude could find itself, and confirm with /context.
4. Check drill. Do one task with a runnable test and one without. Count how often "done" was really done.

## Exit ticket

Put this question to Claude, then paste its answer and your verdict on it:

> Which lines in my CLAUDE.md could you find by reading the code, and which commands verify your work? (Paste your CLAUDE.md.)

**Now question it.** Before accepting the diff, ask Claude what it assumed. Which assumption would your tests not catch?
