# Session 19: Production evals and observability

Level 5: Expert (beyond 100). Deliverable: An eval suite with a held-out score, an LLM-grader check and a tracing setup. Worth: pass or fail, no points.

Contents: Goal and outcomes, Key points, Plain-language glossary, Eval vocabulary, Choosing a grader, Build the suite, What to log per request, Noise and contamination, Worked demo: gate a change on the suite, Common mistakes, Cheat sheet, Exercises, Case to attempt, Vocabulary, Score ladder (what your work looks like at each level), Going further, Study sources, Self-check questions, Exit ticket.

## Goal and outcomes

**Goal.** The learner builds an eval suite that gates every change and wires tracing so a production failure can be found and turned into a test.

**You will be able to:**
- Build an eval with graded trials, real failures and a held-out set
- Choose graders (code, LLM, human) and test an LLM grader against human grades
- Trace requests, tools and cost, and turn a production failure into a new test

## Key points

- Criteria first. Success criteria are specific, measurable, achievable and relevant. An eval is a set of tasks, run as trials and scored by graders. Run several trials per task, because outputs vary.
- Choose the grader. Code is fast and objective but brittle. An LLM grader is flexible: test its reliability against human grades before you scale it. Human grading is slow, so use it sparingly. Many automated cases beat a few hand-graded ones.
- Build from failures. Start with real failures, then add edge and adversarial cases. Keep a held-out set you never tune on. Read transcripts: a score alone does not say why a run failed.
- Evals are noisy. Infrastructure differences alone can move agentic scores by several points, so fix the environment, repeat runs and compare against a baseline. A model that can find the answer key can score without solving the task.
- Observability. Trace each request and tool call with OpenTelemetry. Log tokens, cache reads, latency, cost, stop reason and the prompt version for every request, attributed by feature or workspace, and build new evals from real traffic.

| Term | Meaning | Think of it as |

| Eval | A repeatable test that scores outputs against criteria | A driving test |
| Trial | One run of one task | One attempt at the test |
| Held-out set | Cases you never tune on | The sealed exam paper |
| Trace | The step-by-step record of a run | A flight recorder |

## Eval vocabulary

| Term | Meaning |
|---|---|
| Task | One test: inputs and a success rule |
| Trial | One run of a task. Run several |
| Grader | Code, an LLM or a person that scores a trial |
| Transcript | The full record of a trial: outputs, tool calls, reasoning |
| Harness | Infrastructure that runs, records, grades and aggregates |

Read transcripts, not just scores.

## Choosing a grader

| Grader | Strength | Weakness |
|---|---|---|
| Code | Fast, objective, cheap | Brittle on valid variations |
| LLM | Flexible, scales | Test its reliability first |
| Human | Highest quality | Slow and costly: use sparingly |

Many automated cases beat a few hand-graded ones.

## Build the suite

1. Write measurable success criteria.
2. Collect real failures first.
3. Add edge and adversarial cases.
4. Hold out a set you never tune on.
5. Run several trials and read the transcripts.
6. Gate every prompt, model or tool change on the suite.

Report the held-out score, not the tuning score.

## What to log per request

| Field | Why |
|---|---|
| Tokens and cache reads | Cost and cache health |
| Latency | User experience and timeouts |
| Stop reason | Truncation and refusals |
| Tool calls and results | Debugging agents |
| Model, effort, prompt version | Attribute a change to its cause |

Attribute by feature or workspace.

## Noise and contamination

- Fix the environment before you compare runs.
- Repeat runs and report the spread.
- Compare against a baseline.
- Check that the model cannot look up the answer key.
- Rerun the suite whenever a model changes.

A gain smaller than the noise is not a gain.

## Worked demo: gate a change on the suite

Run this yourself on your own material.

| Step | Do this | What it shows |
|---|---|---|
| 1 | Write three measurable criteria for one workflow | For example 95 percent field accuracy |
| 2 | Run 20 cases with code graders where possible | Report per-case results, not only the total |
| 3 | Change the prompt and rerun on the held-out cases | The suite decides, not a feeling |
| 4 | Find one failed run in the trace and add it as a test | Failures become permanent tests |

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Scoring one run | Outputs vary between trials | Run several trials |
| Tuning on every case | The score overfits | Keep a held-out set |
| Trusting an LLM grader untested | It may disagree with people | Check it on ten graded cases |
| Looking only at the total | It hides why runs fail | Read the transcripts |

## Cheat sheet

**Know**
- Criteria first: specific and measurable.
- Code grader first, LLM next, human last.
- Real failures first, then edge and adversarial. Hold some out.
- Trace tokens, latency, stop reason and tool calls for every request.

**Do**
- Write criteria and 20 cases.
- Grade, and check the LLM grader on ten cases.
- Report the held-out score.
- Turn one failure into a new test.

## Exercises

1. Write measurable success criteria for one of your workflows. Collect 20 real or realistic cases: typical, edge and adversarial.
2. Grade the cases with code where possible and an LLM grader elsewhere. Compare the LLM grader with your own grades on ten cases.
3. Hold out five cases. Tune on the rest, then report the held-out score.
4. Add tracing or request logging. Pick one failed run and turn it into a new test case.

## Going further

- Anthropic reports that infrastructure configuration alone can move agentic coding scores by several points, so compare runs only in a fixed environment.
- Claude Code exports metrics and events through OpenTelemetry when enabled, including token usage, cost, tool decisions and API errors. Events share a prompt id so one prompt can be traced end to end.
- Prompt text, tool arguments and responses are redacted by default. They appear only if you set the log variables, so decide deliberately what you record.
- For Managed Agents, the Usage and Cost Analytics API can group usage by agent or by session.
