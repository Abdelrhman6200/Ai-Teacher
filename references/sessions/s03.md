## Goal and outcomes

**Goal.** The learner picks a model and effort level from evidence, not from the name.

**You will be able to:**
- Describe each current tier and what Anthropic positions it for
- Choose between the two starting approaches (capability-first from Opus 5.5, efficiency-first from Haiku 5.5) and tune effort before switching model
- Run a scored model bake-off with a rubric written beforehand
- Check a model's lifecycle before depending on it

## Key points

- Fable 5.2: demanding reasoning and long-horizon agentic work. Opus 5.5: long-running agentic coding and knowledge work. Sonnet 5.5: the best combination of speed and intelligence. Haiku 5.5: high-volume, latency-sensitive work such as classification, extraction and routing.
- Anthropic's guidance gives two ways to start. Capability-first: start with Opus 5.5 (where most workloads start), then lower effort or move down as the workflow matures, and move to Fable 5.2 if evals at xhigh or max effort still fall short on demanding reasoning or long-horizon agentic work. Efficiency-first: start with Haiku 5.5 and upgrade only where there is a specific capability gap.
- All four list 1M context, 128K max output, text and image input, vision and tool use. Thinking is adaptive on all four and always on for Fable 5.2 and Opus 5.5.
- API prices per million tokens, input and output: Fable 5.2 $8 and $40, Opus 5.5 $4 and $20, Sonnet 5.5 $2 and $10, Haiku 5.5 from $0.10 and $0.50.
- Fable 5.2 and Mythos 5.2 are the same underlying model. Mythos is available through verification programs; Fable carries safeguards for cybersecurity and biology.
- Effort trades intelligence for latency and cost within one model, and the docs say tuning it is often a better lever than switching models. API defaults: high for Fable 5.2 and Sonnet 5.5, medium for Opus 5.5 and Haiku 5.5. If a model overthinks, lower the effort rather than adding instructions.
- Every model has a lifecycle (active, deprecated, retired). Anything pinned to a retired model ID stops working. Read it from the List Models endpoint (lifecycle, deprecated_at, retires_at). The retires_at date can be revised, and a past date on a deprecated model means retirement is overdue, not done. Example: Claude Sonnet 4.5 is deprecated and retires on 30 November 2026.
- Fable 5, Mythos 5 and Sonnet 5 use a newer tokenizer that produced about 30 percent more tokens for the same text at launch, and Haiku 5.5's tokenizer also produces more tokens than Haiku 4.5's. Count tokens on your own text and compare cost per task, not price per token.

## Two ways to start

| Approach | Start with | Then |
|---|---|---|
| Capability-first | Opus 5.5, where most workloads start | Lower effort or move down as the workflow matures. Move up to Fable 5.2 if evals at xhigh or max effort still fall short. |
| Efficiency-first | Haiku 5.5 | Upgrade only where there is a specific capability gap. |

Decide which approach fits your own workload and why.

## Effort before model

1. Write success criteria and a small eval set.
2. Run at the default effort. Defaults: high for Fable 5.2 and Sonnet 5.5, medium for Opus 5.5 and Haiku 5.5.
3. Scores good but slow or costly: lower the effort and rerun.
4. Scores short: raise the effort one step and rerun.
5. Still short: change model, then rerun.

Effort is often a better lever than switching models. Confirm the defaults on the model page.

## Model lifecycle

| Status | Meaning | Action |
|---|---|---|
| Active | Supported | Use it and keep watching the page |
| Deprecated | Has a retirement date | Test the replacement on your eval, then switch before the date |
| Retired | Calls with that model ID stop working | Fix now: anything still pinned is down |

Ties to the lifecycle check in the live task.

## Worked demo: a scored bake-off

Run this yourself on your own material.

| Step | Do this | What it shows |
|---|---|---|
| 1 | Write a 1 to 5 rubric first: accuracy, completeness, format, usable without edits | Criteria before outputs, so style cannot sway the score |
| 2 | Run one real task on Haiku 5.5, Sonnet 5.5 and Opus 5.5 | Same prompt, same input, nothing changed |
| 3 | Score blind where possible and note the tokens used | If scores tie, the cheaper model wins |
| 4 | Rerun the best model at lower and higher effort | Effort is often a better lever than switching model |

## Common mistakes

| Mistake | Why it happens | Fix |
|---|---|---|
| Choosing by name or price alone | The name does not tell you fit | Score a sample of your own tasks |
| The top model for every call | Cost scales with volume: 80 times in the worked example | Route bulk work to cheaper tiers |
| Adding instructions to stop overthinking | It treats the symptom | Lower the effort first |
| Ignoring lifecycle | Anything pinned to a retired ID stops working | Check status and replacement for every model you call |

## Cheat sheet

**Know**
- Fable 5.2 demanding. Opus 5.5 long-running. Sonnet 5.5 balanced. Haiku 5.5 high-volume.
- Start capability-first (Opus) or efficiency-first (Haiku).
- Tune effort before you switch model.
- Check lifecycle: active, deprecated, retired.

**Do**
- Write the rubric first.
- Run five real tasks across the tiers and score blind.
- Rerun the best at lower and higher effort.
- State the escalation rule.

## Exercises

1. Bake-off. Take five real tasks from the learner's job: summarise, extract a table, rewrite for tone, reason through a problem, plan a multi-step task. Write a 1 to 5 rubric first (accuracy, completeness, format, usable without edits). Run each on Haiku 5.5, Sonnet 5.5 and Opus 5.5, then rerun one task at lower and higher effort on the same model, and the hardest on Fable 5.2 where the plan allows. Score blind where possible.
2. Lifecycle check. Look up one model the learner's tools call and find its status and replacement.

## Going further

- Both starting approaches are valid. What matters is that moving up or down is triggered by scores, not intuition.
- Combine tiers: an executor that escalates hard decisions to an advisor, or an orchestrator that hands bulk work to cheaper workers.
- Think in cost per finished task, not cost per token. A cheaper model that needs retries can cost more overall.
- Keep the rubric and test set so the bake-off can be rerun whenever a model or price changes.
